Findings and implemented corrections
1. The earlier exact-origin redirect/CORS/CSRF fixes are present in code and tested.
   Both providers reject other hosting tenants, arbitrary loopback origins/ports,
   userinfo URLs and scheme changes; saved redirects are revalidated at callback.
   Cookie mutations require exact configured Origin, or trusted Referer only when
   Origin is absent. Bearer-only clients remain supported. A bearer header cannot
   bypass CSRF if the cookie supplies authentication. Request Host is not trusted.
2. OAuth state was not bound to the initiating browser. Ten new HTTP regressions
   failed before the correction (audit-state-before.log); all now pass. Each provider
   now has a 10-minute HttpOnly, Path=/, SameSite=Lax binding cookie containing the
   state hash. Production adds Secure and a __Host- prefix; no Domain attribute is
   set. Callback verifies the hash with timingSafeEqual BEFORE provider exchange.
   Other-browser, mismatched, wrong-provider, malformed and missing state fail closed.
   Matching callbacks clear the binding; denial also deletes the stored state.
   Database expiry and single-use deletion remain enforced. Same-provider concurrent
   login attempts intentionally replace the cookie; only the latest can complete.
3. First-time sign-in was broken under the restricted database role: both OAuth
   services created a workspace without transaction-local app.current_user_id.
   Two real PostgreSQL tests reproduced error 42501/RLS (audit-provisioning-before.log).
   Both services now set the new user's RLS identity inside the existing provisioning
   transaction, before creating the organization/OWNER membership. No RLS policy,
   role privilege or database schema was weakened. Verified identity linking,
   returning identities and Google unverified-email non-linking are covered.
4. Session cookies remain HttpOnly, host-only and Secure in production. Creation
   and deletion now share options. Production previously used None for creation
   and Lax for clearing; cookie identity already matched by name/path/domain, but
   policy flags were inconsistent. SESSION_COOKIE_SAME_SITE=lax|none now lets the
   release choose a policy; omitted preserves production None and development Lax.
   Explicit none without production Secure is rejected. Invalid names are rejected.
   Invalid/expired/revoked cookie sessions receive 401 and an expired clearing cookie.
   /v1/me and logout use Cache-Control: no-store. Session creation stores only a hash.
5. Browser sessions are not adopted from URLs or persisted in localStorage. Legacy
   tokens are discarded/removed. OAuth uses full-page navigation, with no token
   broadcast/postMessage/storage-event relay. App startup revalidates /v1/me before
   rendering authenticated content. Manual development tokens remain memory-only.
   API calls retain credentials: include. Failed logout now rejects instead of
   pretending to log out; the UI keeps its session and shows an error. A 401 from
   stale-session logout is handled as signed out because the backend clears it.
6. Session persistence is fixed at seven days. validateSession checks revocation
   and absolute expiry and may update lastActiveAt after 60 seconds; it does NOT
   extend expiry or rotate the token. There is no refresh endpoint or OAuth refresh
   token persistence. Reload/repeated /v1/me retain the user until expiry; users
   reauthenticate afterwards. This existing policy was verified, not expanded.
7. Organization controllers use AuthGuard and service-level membership/OWNER checks
   within RLS tenant/user context. Existing role/isolation tests pass. Both SSE
   aliases verify the current user/org membership before opening, including VIEWER
   access. Live streams now end at 30 seconds or earlier captured session expiry;
   native EventSource reconnect re-enters session and membership checks. No database
   transaction stays open for the stream. Revocation/removal exposure is bounded to
   the current connection's remaining lifetime, not eliminated instantaneously.
   Real Chromium tests observe final failed reconnect after approximately 34 seconds
   (30-second connection plus browser retry delay) for both revocation and removal.
8. Development defaults had mismatched localhost frontend vs 127.0.0.1 callbacks.
   Defaults and .env.example now use localhost consistently so host-only state and
   session cookies survive the round trip. Actual existing .env files were untouched.
   Existing local configurations still need the alignment check in the checklist.

Cloudflare/Render deployment: actual expected cookie behavior
Evidence: render.yaml sets the API at relayforge-staging-api.onrender.com,
FRONTEND_URL at relayforge-staging-web.onrender.com and frontend VITE_API_URL at the
Render API. Both Wrangler files configure static SPA assets, without a proxy handler
or run_worker_first. The repo does not identify a live Cloudflare account hostname
or establish live dashboard environment overrides, so those were not assumed.

The authoritative Public Suffix List contains onrender.com, workers.dev and pages.dev.
Consequently the two distinct Render hosts are DIFFERENT sites, despite sharing an
onrender.com suffix. Any Cloudflare-default frontend to the Render API is cross-site
too. At top-level navigation to the API, state cookies can be set, and SameSite=Lax
allows the top-level GET callback from Google/GitHub. The callback can set a Secure
API session cookie. After redirect to the frontend, however, /v1/me and SSE requests
to the API are third-party contexts. With None plus credentials they can work only
when browser policy permits them. With third-party cookies blocked they carry no
usable API session and /v1/me returns 401. Lax also omits the cookie on these cross-
site fetches regardless of the CORS allowlist. CORS cannot override cookie policy.
Trying to share Domain=onrender.com is prohibited by its public-suffix status.

A Cloudflare frontend also needs FRONTEND_URL changed from the Render frontend to
its exact public origin, otherwise redirects fall back to Render and CORS rejects
its requests. The actual live settings/consent registrations were not modified or
asserted. This patch preserves legacy None by default; it does not claim default
hosting now works with third-party-cookie blocking.

Recommended solutions (configuration/proxy proposals, not deployed):
A. Bind Cloudflare frontend app.relayforge.example and Render API api.relayforge.example
   to owned HTTPS custom domains. These share a schemeful site while remaining
   different origins. Use host-only API cookies, SESSION_COOKIE_SAME_SITE=lax,
   exact frontend CORS, and credentialed requests. Do not widen the cookie Domain.
B. Proxy /auth/*, /v1/* and /health/* at the exact frontend origin F to one fixed
   Render upstream, and build with VITE_API_URL=/. Configure public provider callback
   URLs through F. Cookie Set-Cookie headers are then interpreted against F, making
   the host-only cookie first-party for both the SPA and API paths. Cloudflare needs
   a reviewed Worker fetch handler, ASSETS binding, and assets.run_worker_first route
   patterns so the SPA fallback cannot absorb callbacks/API requests. Forward method,
   body, query, browser Origin/Referer and Cookie, preserve separate Set-Cookie headers,
   status/Location and streaming bodies, use upstream redirect: manual, and disable
   auth caching/buffering. Upstream must be fixed (e.g. nonsecret API_ORIGIN), not
   browser-selected. The local browser suite exercises the same-origin Vite proxy
   using VITE_API_URL=/ and DEV_API_PROXY_TARGET; it does not certify a Cloudflare
   production Worker that has not been implemented/deployed.
See auth-release-checklist.txt for exact variable names and provider registrations.

Remaining risks / release conditions
- Choose and provision a same-site/same-origin topology and exact provider callbacks.
  The production proxy/domain work is proposed, not performed. Live environment
  variables and real provider consent still need authorized manual verification.
- Third-party-cookie-blocking behavior on default hosting remains a real deployment
  limitation; do not restore URL/localStorage tokens to work around it.
- Previously exposed sessions remain server-valid until expiry/revocation; no live
  sessions were revoked. Consider a separately authorized operational revocation.
- SSE revocation/removal has up to 30 seconds of residual access on an existing
  connection; immediate server-push disconnect would require further infrastructure.
- The existing dependency advisory still blocks CI/release; actual production TLS,
  Cloudflare proxy behavior and Safari/Firefox were not tested by the local suite.
- Fixed seven-day sessions require sign-in after expiry. XSS/dependency/infrastructure
  hardening beyond the reviewed auth paths is not certified by these tests.
