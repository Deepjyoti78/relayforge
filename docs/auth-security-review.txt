Scope and corrections
- Both OAuth services now trust only the configured FRONTEND_URL origin,
  including scheme and port. Redirect URLs with userinfo are rejected. Invalid
  redirects fall back to FRONTEND_URL. Stored redirects are revalidated during
  callback, covering states created before this patch.
- Google and GitHub callbacks keep the session in an HttpOnly cookie. Session
  tokens are no longer appended to redirect URLs. Successful callbacks set
  Cache-Control: no-store and Referrer-Policy: no-referrer. Internal/provider
  error descriptions are no longer reflected into redirect URLs.
- Browser OAuth uses full-page navigation for both providers. It no longer
  passes tokens through postMessage, BroadcastChannel, storage events, or URL
  parameters. The frontend validates the cookie via /v1/me on every startup.
  Legacy URL tokens are discarded and removed from history. Legacy persisted
  session/popup tokens are removed. The existing development manual-token
  facility uses memory only; it does not survive reload.
- Credentialed CORS permits the exact configured frontend origin. Shared hosting
  suffixes, unconditional loopback origins, malformed origins, and arbitrary
  ports are no longer allowed. Nonbrowser requests without Origin still work.
- Cookie-authenticated mutations require an exact trusted Origin or, only when
  Origin is absent, a trusted Referer. Missing/null/untrusted origins fail closed.
  Bearer-only clients remain supported. A bearer header cannot exempt a request
  authenticated by a cookie from CSRF checks. The request Host is not trusted.
- Both SSE aliases verify membership using the authenticated user and requested
  organization inside tenant context before obtaining the stream. VIEWER members
  remain authorized; nonmembers receive 403 and unauthenticated clients 401.
- Existing integration fixtures send Origin for cookie-authenticated mutations.
  Existing OAuth test mocks were typed so the complete lint check passes.

Environment-dependent release checks still required
- Live Google and GitHub consent, registered callback URLs, redirect back to the
  configured frontend, /v1/me after navigation/reload, logout, and SSE should be
  exercised in staging using authorized test accounts. Provider calls were
  mocked in unit tests; live provider consent was not attempted.
- Cross-site frontend/API hosting depends on third-party-cookie policy even with
  SameSite=None; Secure and fetch/EventSource credentials enabled. In particular,
  distinct hosting-provider domains can be cross-site. Browsers that block those
  cookies may fail sign-in persistence. Validate supported browsers. A same-site
  domain arrangement or same-origin API proxy is the preferred deployment remedy;
  do not restore URL/localStorage session-token delivery as a workaround.
- FRONTEND_URL must equal the actual frontend origin (a path is allowed in the
  configured URL) and use HTTPS in production. Development frontend/API hosts
  must align for Lax cookies; frontend fallback now preserves localhost versus
  127.0.0.1. An explicit VITE_API_URL still takes precedence. No deployment
  environment values or secrets were modified.
- Frontend has no standalone lint/test script. Its module behavior is covered
  through Jest's VM sandbox and its typecheck is included in the build; no
  automated real-browser end-to-end flow was run.

Remaining security risks / follow-up work
- Previously exposed session tokens may already exist in copied URLs, external
  logs, browser history, or other clients. Removing local storage does not revoke
  server-side sessions. An authorized operational session revocation should be
  considered separately; this audit did not revoke users' sessions.
- OAuth state is single-use and expires after ten minutes, but is not bound to
  the initiating browser with a separate cookie. Login-CSRF/session-swapping
  protection remains incomplete and deserves a focused follow-up with provider-
  specific browser-bound state. This patch does not claim to close that issue.
- SSE membership/session authorization is checked at connection time. An already
  open stream is not revalidated when membership is removed or a session is
  revoked/expires. Immediate disconnect/revalidation needs follow-up.
- Origin checks mitigate cookie CSRF, not same-origin XSS. General XSS auditing,
  dependency vulnerabilities, OAuth account-linking policy, and infrastructure
  configuration were outside this targeted patch.
